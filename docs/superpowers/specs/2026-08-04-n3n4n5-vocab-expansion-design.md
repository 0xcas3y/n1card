# N3/N4/N5 词库扩容 + 自动化批量生成脚本 — 设计文档

**日期**：2026-08-04
**状态**：草案
**前置**：`2026-07-16-n1n2-adj-onomatope-design.md`（现有词性拆分模式：数据文件/页面/校验器都是这次要复用的基础设施）
**范围**：N3、N4、N5 三个级别，扩容到对齐官方 JLPT 大纲词量，并按词性拆分成动词/名词/形容词/副词/オノマトペ 5 个子库，结构对齐 N1
**明确排除**：
- **N2 不在本次范围**——用户手头有自己整理的 N2 词表，之后会像当初 N1 的 `raw-words.txt` 一样直接提供给我，走现有的人工/半人工批次生成流程，不需要本次新建的自动化脚本去"找词表"
- 学新批次/时间窗/强制测验等学习流程——新增的词库沿用 `2026-07-16` spec 定的自由刷卡 + 测验简化模式，不复制动词那一整套分批体系
- 回忆模式——已在 `2026-08-03-recall-mode-design.md` 之后被移除，本次不涉及

---

## 1. 目标 & 动机

现在 N3/N4/N5 各只有一个单一文件（300/150/80 词，且已经全部是纯动词，见 §2.1），跟 N1 的 2267 词、5 个词性子库差距巨大。用户希望把这三级也扩到接近官方 JLPT 大纲的词汇量级，结构上和 N1 完全对齐。

由于目标量级很大（N3≈3750、N4≈1500、N5≈800，对比现有 N1 全部词性加起来才 2267），沿用之前"每批 30-70 词人工对话生成"的方式跑不完——本次要新建一个调 Claude API 的批量生成脚本，人工只做抽查校对，不再逐条参与生成。

**执行顺序**：N5 → N4 → N3（从小到大，先在最小的 N5 上把"词表来源 → 脚本生成 → 校验 → 抽查 → 入库 → 建页面"整条流程跑通并验证质量，再复用到 N4、N3）。

## 2. 数据

### 2.1 现状核查

`cards-n3.json`（300）/`cards-n4.json`（150）/`cards-n5.json`（80）**已经是纯动词库**——每条都带 `type`（五段/一段/サ変/カ変），跟 N1 的 `cards.json` 是同一种角色。不需要拆分或重新分类，直接作为三个级别各自的"动词"子库继续扩容即可。

### 2.2 新增数据文件

```
data/cards-n5-noun.json      data/cards-n5-adj.json      data/cards-n5-adverb.json      data/cards-n5-onomatope.json
data/cards-n4-noun.json      data/cards-n4-adj.json      data/cards-n4-adverb.json      data/cards-n4-onomatope.json
data/cards-n3-noun.json      data/cards-n3-adj.json      data/cards-n3-adverb.json      data/cards-n3-onomatope.json
```

Schema 和现有文件完全一致，复用 `scripts/validate-cards.js`，不改校验器。

### 2.3 目标词量

对齐官方 JLPT 大纲总词量（各家统计口径略有差异，取大致量级）：

| 级别 | 目标总量 | 现有动词库 | 缺口（其余 4 个词性合计） |
|---|---|---|---|
| N5 | ~800 | 80 | ~720 |
| N4 | ~1500 | 150 | ~1350 |
| N3 | ~3750 | 300 | ~3450 |

**名词/形容词/副词/オノマトペ 4 类之间怎么分配缺口**：不预设固定比例——每一批的实际产出以"能从可靠词表里找到多少该词性、该等级的真实词"为准，不强行凑数。N1 的现有比例（动词27%/名词28%/形容词23%/副词12%/拟声词10%）可以作为初期参考，但不是硬指标。

### 2.4 词表来源

**优先本地已有材料，本地没有的部分用公开权威 JLPT 词表补齐**：

- 已核查 `~/Downloads/JLPT/` 只有 N1、N2 相关教材 PDF（`日本語の森 JLPT N2 この一冊で合格する.pdf` 等），**没有 N3/N4/N5 的本地材料**
- 因此 N3/N4/N5 的原始词表基本依赖公开可查的权威 JLPT 词汇表（各词性分类需要在词表基础上再做词性标注/筛选）
- 每个词性、每个级别先出一份"原始词表"（纯词条列表，格式参考现有 `data/raw-words.txt`），再喂给生成脚本

### 2.5 内容生成

新建 4 个 prompt 模板（`data/prompts/generate-batch-n{3,4,5}-{noun,adj,adverb,onomatope}.md`，复用 `2026-07-16` spec 里已经跑通的 adj/adverb/noun/onomatope 版本作为基础），相对 N1 版本的调整：

- **难度下调**：例句用词、句式复杂度要匹配对应等级（N5 例句应该是简单句，不能出现 N1 词汇）
- **助记法风格不变**：沿用"拆音节 + 组成迷你日语短语 + 中文记忆钩子"的 phrasal narrative 写法（`generate-batch.md` 里定义的三条硬指标：音准、短语通顺、含义钩子）
- **拟声词 `word === kana`** 的约定不变

### 2.6 生成脚本（新增基础设施）

新建 `scripts/generate-cards.js`：

- 输入：一批原始词条（纯文本列表）+ 对应的 prompt 模板 + 起始 id
- 调用 Claude API（批量，每批数量视 API 单次响应稳定性调整，初期建议先在 N5 上试小批量摸出合适的 batch size）
- 输出直接追加/合并进对应的 `data/cards-*.json`
- 生成后自动跑一遍 `scripts/validate-cards.js` 校验格式，格式不过的批次不写入
- **不做语义正确性的自动校验**——格式对不代表内容对（读音、词性、释义、例句是否准确），这部分只能人工抽查，抽查比例和方式留给实现阶段决定

## 3. 页面 & 导航

比照 `2026-07-16` spec 的模式：

- 新增 12 个 HTML 页面：`n5-noun.html`/`n5-adj.html`/`n5-adverb.html`/`n5-onomatope.html`（N4、N3 同理各 4 个），结构和 `n1-noun.html` 等完全一样，只是注入的 `LEVEL_NAME`/`CARD_DATA_URL` 不同
- `index.html` 里 N3/N4/N5 三个入口的 `href` 从直接指向 `n3.html`/`n4.html`/`n5.html`，改成指向现有的 `word-type-picker.html?level=n{3,4,5}`（这个页面已经是通用的、靠 `?level=` 驱动，N1/N2 已经在用，直接复用不用改）
- `word-type-picker.html` 目前的三个选项（动词/形容词/拟声词）需要扩展成五个（动词/名词/形容词/副词/拟声词），这个改动会同时影响 N1/N2/N3/N4/N5 五个级别的选择页（因为是同一份文件），需要确认 N1/N2 现在也都有名词/副词子库了（已有：`cards-n1-noun.json`/`cards-n1-adverb.json`；N2 目前没有名词/副词子库——这属于"N2 不在本次范围"，选择页对 N2 来说这两个选项会指向不存在的文件，需要在实现阶段处理：要么 N2 词性选择页暂时只显示已有的三个选项，要么先放着等 N2 词表来了再补，具体做法留给实现计划）

## 5. 测试

### 5.1 自动化

- `npm run validate` 需要能跑通所有新增数据文件（当前脚本只认单文件参数，需要支持批量/glob，或者实现阶段决定别的做法）
- 生成脚本本身如果包含任何纯函数逻辑（比如批次切分、id 分配），需要单元测试；调 API 的部分不写单元测试（不 mock API，前例 `scripts/plan.test.js`/`scripts/recall.test.js` 的风格是只测纯函数）

- [ ] N5 词表来源确定，能拿到名词/形容词/副词/拟声词的原始词条列表

- [ ] N5 四个新页面能正常访问、自由刷卡、测验
- [ ] `index.html` → N5 → 词性选择页 → 五个选项都能进对应页面
